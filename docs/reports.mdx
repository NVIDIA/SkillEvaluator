This page maps everything SkillEvaluator writes to disk and how to read it.
Nothing here requires an API key — it is the output contract for every command,
from a keyless `quality-check` to a full live evaluation.

Two kinds of artifacts exist. Tier 1 and Tier 2 commands render **reports** —
one per format, selected with `-r`. Tier 3 (`tier3 evaluate`) additionally
writes a **results tree**: a timestamped directory of raw scores, trials, and
lift data that `view` and `compare` read back later.

[Harbor](https://github.com/harbor-framework/harbor) is the open-source agent
evaluation framework that runs those Tier 3 trials. SkillEvaluator collects its
job artifacts into the results tree described on this page.

## Retained three-tier CI evidence

The opt-in all-tier workflows retain one aggregate artifact for 14 days. GitHub
names it `skill-evaluator-results-attempt-N`; GitLab retains the aggregate job's
`skill-evaluator-results/` directory. The trusted feedback comment links the
actual artifact download for that run. Authentication and artifact expiry still
apply; this link does not imply publicly hosted HTML.

The PR or MR comment presents one summary table with a row for each skill.
Each row shows a one-line status, issue count and the most important available
finding or blocker for **Tier 1 — Static and Security Validation**,
**Tier 2 — Deduplication** and **Tier 3 — Live Agent Evaluation**. A single
**Report** link per skill opens the combined report artifact for that run;
download and extract it, then open `index.html` to inspect the detailed aggregate
and native reports. The comment keeps tier details in those reports rather
than adding separate tier sections or report links.

This schematic shows the information in a row; real results supply the statuses,
counts, findings and authenticated **Report** link:

| Skill | Tier 1 — Static and Security Validation | Tier 2 — Deduplication | Tier 3 — Live Agent Evaluation | Combined report |
| --- | --- | --- | --- | --- |
| `skills/example` | Passed · 0 issues | Failed · 1 issue · duplicate content found | Incomplete · issues unknown · paired evidence missing | Report |

Issue counts summarize unique actionable findings plus independent validation
errors and warnings from retained native evidence; informational notes and
configuration-only scope notices are excluded. Incomplete or missing evidence
shows an unknown count; it cannot imply zero findings or a completed check.
The Tier 1 gate and each advisory tier's status stay separate, so this example
can pass the required CI gate while still needing review of Tier 2 and Tier 3.
Every tier selects the same skills: the changed skills, or every skill when
the pull request changes CI setup under `.github/`, `.gitlab/`,
`.skillevaluator/ci` or `.gitlab-ci.yml` (on GitHub, also when it changes more
files than the API can list). A cell for a skill that its tier did not select
reads `Skipped · issues unknown · Not selected for this tier`.

```text
ci-results.json
index.html
source-attempts.json   # GitHub: run attempt whose artifact supplied each tier
summary.md
tier1/                 # hardened scanner reports, including summary.json
tier2/ci-tier.json
tier2/skill-001/       # native retained JSON and HTML
tier3/ci-tier.json
tier3/skill-001/       # native retained JSON and HTML
  diagnostics/        # redacted worker logs when execution failed or is incomplete
```

`ci-results.json` uses report contract `skillevaluator-ci-v1` and records the
repository, exact commit, platform, run ID, attempt, environment, and each
tier's required/advisory policy: Tier 1 has `required: true`, while Tier 2 and
Tier 3 have `required: false`. On GitHub, each tier with retained evidence
records `source_attempt`, the run attempt that produced it; after **Re-run
failed jobs** it can be earlier than the aggregate's own attempt. A tier can be
`passed`, `failed`, `incomplete`, `skipped`, `not_run`, `needs_action`, or
`neutral`. `neutral` means Tier 3 paired execution completed with a neutral
dimension-based verdict; Skill Lift has its own independent diagnostic band.
Like every Tier 3 status, it is advisory. Failed,
incomplete or missing Tier 1 evidence fails the aggregate. Tier 2/3 failures and
incomplete results remain advisory and retain their native status; a passing CI
gate does not mean those tiers passed. A check that never executed cannot become an empty success.
The deprecated Tier 3 required settings are ignored in CI. Standalone validation
and benchmark publication retain their separate policies.

Tier 2 reports retain deduplication and catalog-similarity findings;
Tier 3 reports retain paired scores and coverage, Skill Lift, attempts,
latency/resource metrics and available trial links. Download and extract the
artifact, then open `index.html` to inspect the aggregate and native reports.
Detailed files remain available even when a tier fails or needs configuration.
When a native skill's execution fails or is incomplete, or its worker exits
abnormally, the skill retains bounded, redacted worker, Docker and
agent-installation diagnostics under `diagnostics/`, even if no canonical report
was produced or its verdict is failed. A complete run with a failed or neutral
verdict retains none. The worker's `command.log` comes first, then logs from
one trial of each Harbor job (a failing trial when there is one), at most four
trials per skill, with failing trials chosen before passing ones. All
skills of one tier share a limit of 1000 diagnostic files and 16 MiB. Each
`index.json` records retained, omitted and truncated files, including those
omitted at a limit.
Catalog failures retain diagnostics under `tier2/catalog/diagnostics/`.
Agent trajectories, credentials and runtime configuration are excluded.
The publisher renders validated retained JSON; it does not execute artifacts
or trust candidate-provided HTML in its privileged feedback job. Optional
report hosting is independent from these private artifact links.

## Report formats

Every Tier 1 and Tier 2 command accepts `-r`/`--report` and `-o`/`--output-dir`.
The flag is repeatable and accepts comma- or space-separated values
(`-r cli,json,html` or `-r cli json html`). By default — with no `-r` at all —
the terminal shows a compact summary and the run writes `html` and `json`
report files. An explicit `-r` is honored exactly, including `-r cli`, which
prints the full terminal report and writes no files. Files land in `reports/`
unless you override it with `-o`. Report output must be outside the source tree
whose publication identity it describes. When the default `reports/` would be
inside the target (for example, after `cd my-skill`), SkillEvaluator safely
reserves the sibling directory `my-skill-reports/` instead. A catalog uses the
same rule and relocates to `<catalog>-reports/`. An explicit in-target `-o` is
rejected; choose an external directory instead. Existing nonempty sibling
directories are reused only when their SkillEvaluator ownership marker is
valid, preventing the default from overwriting an unrelated directory.
For Tier 3, an output directory inside the target repository or an included
skill root must likewise be new, empty, or already carry a valid ownership
marker. This applies to linked-context staging as well as `--copy-repo`. A
nonempty unowned directory is rejected so selecting an authored subtree cannot
silently remove that subtree from the agent's runtime context.

For compatibility, commands launched from a parent directory keep the familiar
layout when the default output is safe to claim: `skillevaluator validate
./my-skill` writes to `./reports/` when that directory is absent, empty, or
already authenticated as SkillEvaluator output. If `./reports/` is nonempty
and unowned, the default relocates to `./my-skill-reports/` instead of writing
into unrelated content.

For `validate`, that compact default is a pipeline view — a per-check ticker
plus a summary. Pass `--verbose` to get the full per-check detail stream in
the terminal instead. Final panels are written to stdout. When output is
redirected or running in CI, tier and check starts, stage changes, measured
completion counts, and completion lines remain visible on stderr. Unchanged
updates are omitted; a running stage emits a heartbeat after 60 seconds without
progress. Counts describe observed work, without estimating a completion
percentage. Interruption tears down the progress display and its worker.

Terminal grades use green for A/B, amber for C, and red for D/F; failed,
incomplete, and unavailable evidence retains its status treatment. Lift that
rounds to zero is neutral. At narrow widths, condition labels, numeric scores,
and their complete bars stack together. The full terminal summary includes
successful quality and lift evidence in Details. Artifact paths use the emitted
filenames and become clickable only on capable interactive terminals; plain,
no-color, redirected, and string-rendered output retains readable paths.

| Format | What it is | Reach for it when |
| --- | --- | --- |
| `cli` | Full Rich terminal report | You want every finding at the keyboard, no files written |
| `json` | Machine-readable JSON (default) | CI needs to parse scores and findings |
| `html` | Standalone HTML report (default) | A human needs to review or archive a run |
| `markdown` | Markdown for PR comments | You want the result posted on a pull request |
| `sarif` | SARIF 2.1.0 JSON | GitHub Code Scanning or other SARIF consumers need inline annotations |

```bash title="One run, four report files"
skillevaluator validate ./my-skill -r json,html,markdown,sarif -o reports
```

For gating a pipeline on the JSON output, see [Gate Your CI](ci-integration.mdx).

## Reading the final status

The compact terminal summary, full terminal report, and HTML header describe the
same command outcome: **Passed required checks**, **Changes required**, or
**Incomplete**. A confirmed failure takes precedence over missing evidence.
Advisory tiers retain their own findings and execution status without changing
the required gate or process exit code.

**Publication eligibility** is a separate, stricter assessment of the recorded
policy, provenance, and evidence coverage. A passed required gate does not imply
publication eligibility. Standalone Tier 3 reports show **Not assessed (Tier 3
only)**. **Best agent score** describes one evaluated agent, rather than approval
of the whole validation run.

Each tier counts its own passed, failed, incomplete, skipped, and N/A results.
Skipped and explicitly inapplicable checks are excluded from executed-check
denominators. A tier that produced no results is **Not run**; presentation of an
unrequested tier does not create evidence that it ran.

Tier 3 summaries prefer recorded per-condition counters: for example,
**188 scored trials: 101 with skill, 87 baseline**. Condition details retain
expected counts and execution status, so partial execution and early stopping
remain distinguishable. Missing or malformed counters are **unavailable**, and
explicitly skipped arms remain **skipped**. Legacy reports with trial rows but
no counters show **retained rows**, which are observations rather than complete
scored totals. Preview limits and physical retry rows do not replace recorded
attempt counts. These are display projections; canonical JSON and evaluation
payloads are unchanged.

### Tier 2 comparison scopes and evidence

The HTML Tier 2 view separates **Within this skill** (redundant content among
its files) from **Across skills** (catalog or collection comparisons). Each
scope shows Checks completed, Duplicate findings, Affected files or skills,
and Catalog entries compared. Completion uses recorded comparison
evidence; a completed check can still fail its gate because it found duplicates.
Refused LLM classifications and file safety errors remain visible findings,
but do not count as confirmed duplicates within a skill.

A completed comparison with no matches shows zero. A skipped catalog comparison,
missing metadata, or an incomplete scan shows the recorded reason and unavailable
counts. Target against catalog comparisons exclude the target's recorded self
entry. Within-skill checks and recorded pairwise scans mark Catalog entries compared
as not applicable. Pairwise scans identify the collection size separately. Affected counts use recorded file or skill paths,
so equal display names do not merge distinct skills. Token or context savings
are not estimated from duplicate counts.

HTML, terminal, and Markdown reports link every recorded Harbor job to its
**Results** and available **Analysis**, using the job's recorded name or
`Job N` when no name is available. Legacy single-job and analysis-only links
remain usable. Job names do not establish which agent or condition produced a
job. Links use the existing URL validation and output escaping.

HTML disclosures show recorded scanner versions and LLM provenance, plus
sanitized model, evaluator, dataset digest, and evaluated source metadata under
Tier 3 Diagnostics. Missing values remain unavailable. These views use existing
report data and do not read the source tree or contact providers while rendering.
Full downloads and preview omission counts remain available; with-skill token
charts are labeled separately from the resource table's two-arm comparisons.

## File naming

Report filenames follow two patterns, both under the output directory:

| Command | Basename | Overwrites? |
| --- | --- | --- |
| `validate` (full run) | `skillevaluator-output-<timestamp>` | No — each run gets a new, sortable name |
| `quality-check` | `skillevaluator-quality` | Yes — fixed name per format |
| `rubric-eval` | `skillevaluator-rubric` | Yes |
| `security-scan` | `skillevaluator-security` | Yes |
| `pii-scan` | `skillevaluator-pii` | Yes |
| `lint-scripts` | `skillevaluator-script-lint` | Yes |
| `similarity-check` | `skillevaluator-similarity` | Yes |
| `context-optimization-check` | `skillevaluator-context` | Yes |
| `dedup-scan` | `skillevaluator-dedup` | Yes |

The extension matches the format (`.json`, `.html`, `.md`, `.sarif.json`); the `cli` format
prints to the terminal and never writes a file. A full `validate` run's
timestamp is `YYYYMMDDHHMMSS`, so
`-r json` produces something like `skillevaluator-output-20260709141530.json`
and never clobbers the previous run.

## HTML report

The HTML report is one self-contained file. It opens on the answer and puts
the evidence below it:

- **Header.** The skill name is the page title. The header shows one verdict,
  the date and version, and **Download JSON**.
- **Summary.** The verdict with a one-line reason, four numbers (checks passed,
  findings, blocking critical and high findings, quality score with its
  minimum), and **Fix first**: up to five places to fix, most severe first,
  each linking to its evidence. When a required scanner did not finish, it is
  listed first with the scanner's own reason, such as a timeout. Two scanners
  reporting the same file and line take one entry.
- **Findings and evidence.** Every check with its findings and suggested fixes.
  Failed checks come first. Checks that report a raw ID, such as
  `SCRIPT_LINT`, show a plain name with the ID beside it. Scanner diagnostics
  and gate failures are always shown and printed; raw scanner lines that only
  repeat a finding are folded away.
- **Run details.** Scope, the target path, provenance and the gate policy.

Use the sidebar or tier tiles to open a tier. A comprehensive `validate` report
keeps all three tiers visible, including **Not run** and **Not run (not requested)**
when evidence is absent. Targeted reports keep their narrower scope. On small
screens, a sticky tier bar keeps navigation available while reading long evidence.
Tier 3 retains Overview, Insights, Agent Details, Trials, Dataset and Diagnostics.
For its tabs, Left/Right and Home/End move focus; Enter or Space opens the focused
view. Finding links clear incompatible filters, open their evidence and move focus
to the exact finding. Direct agent links open and focus the named agent panel;
section links open at the start of the section.

The **Theme** control offers System, Light and Dark. System follows live device
changes; an explicit choice persists until System is selected again. Reports use
native theme-aware scrollbars and respect reduced motion. Without JavaScript,
all tier and agent evidence remains readable. Printing exposes supporting evidence
and then restores disclosure and filter state when returning to the screen.

Reports use 14-pixel body text with relaxed line spacing, distinct label/value
gaps, and consistent space between cards, findings and table rows. Tier 3 view
tabs wrap on narrow screens; wide evidence tables keep their own horizontal
scroll area. The same reading rhythm applies in Light and Dark themes.

Tier 3 charts include Chart.js 4.5.1 inside the HTML file and work offline;
they make no CDN or source-map requests. Each chart describes its measurements
and links to the underlying data table. If JavaScript or canvas initialization
is unavailable, a visible message points readers to the data. Theme changes and
printing redraw the charts. **Chart software notices** retains the full MIT
licenses for Chart.js and its bundled color library. Tier 1 reports do not
load or embed these chart resources.

A finding is one problem a check reports, with a severity. The same problem
reported on several lines, or in several files or skills, counts once at its
highest severity; each location is an occurrence, including each line a
PII finding lists when one value repeats. When the unique, occurrence and
raw record counts differ, or when some errors or warnings have no finding
behind them, the findings number shows the occurrences, the raw records and
those errors and warnings beneath it, in the same words as the Markdown
report's Total Issues. The workflow scope note for a stage that configuration
skips, such as LLM checks under `--no-llm`, is not counted as a warning there. A finding in a failed check blocks the
verdict; a finding in a passed check is advisory. A quality score below the
configured minimum fails the Quality score check, so it also blocks the
verdict.

The HTML report, the CI index and the Pages history use the same verdict
words: **Passed**, **Changes required**, **Incomplete**, **Skipped** and
**Neutral**. When no check ran, the verdict is Skipped, not Passed. A tier
whose gate does not block, such as deduplication with `--no-block-on-dedup` or
live evaluation without `--block-on-agent-eval`, shows **Failed (advisory)**
when it fails, because it does not require changes. Publication eligibility is
shown separately from the command result. Summary reasons count required and
advisory checks individually, including when a tier contains both. Eligibility is
shown next to the verdict, because a report can pass its checks and still not
be eligible for publication. The report follows the system light or dark theme
until you pick one, and always prints dark text on white paper.

## BENCHMARK.md

When the target is a skill, `validate` always writes `BENCHMARK.md` to the
output directory — regardless of which `-r` formats you picked, and even when
validation fails. It is a decision-first publication card: the overall verdict
and recommendation come first, followed by per-tier evidence, evaluator and
dataset provenance, agent/model details, and a dimension-by-dimension
`Baseline → Skill Uplift` table when Tier 3 ran. Public cards omit validation
profile names and absolute host paths.

Table scores are rounded half-up to one decimal place. A score near a dimension
verdict threshold keeps as many extra decimals as it needs to stay in its band,
so `0.4995` is shown as `49.95%`, not as a passing `50.0%`. Uplift is the
difference of the two displayed scores, so a cell such as
`58.4% → 94.8% (+36.4 points)` always adds up. A score outside 0–1 is shown as
`Not available`.

The card carries one overall verdict — `PASS`, `NEUTRAL`, `FAIL`, or
`INCOMPLETE`. It fails closed: if a required scanner produced no trustworthy
evidence, the verdict is `INCOMPLETE` and the card explicitly says not to use
it to recommend publication. A Publication Recommendation section appears only
on a clean `PASS`; `NEUTRAL` means the evidence is complete but at least one
required dimension remains below the pass band.

Tier 1 is always required for publication. Tier 2 and Tier 3 are also required
by default, so a missing, skipped, or incomplete required tier produces
`INCOMPLETE` rather than a publication recommendation. Catalog orchestration
may explicitly persist `benchmark_policy.tier2_required = false` or
`benchmark_policy.tier3_required = false`; the card discloses each exception
instead of implying that the tier ran. An optional tier that is present but
incomplete still makes the card `INCOMPLETE` because malformed evidence cannot
certify publication. A default-passed result object is not sufficient. Tier 1
and Tier 2 evidence must carry a valid `publication_evidence` marker written by
a built-in command wrapper, and every recognized result must record a success,
finding, or positive check count that proves it executed. Tier 1 must also
cover every default check that applies to the content type: schema, security,
PII, license, code integrity, and Unicode, plus version, quality, and lint for
skills. A run narrowed with `--checks` is reported but cannot certify Tier 1. Legacy and custom
results remain visible, and their failures still block publication, but they
cannot satisfy a required tier or create a waiver. Generic per-result `optional`
metadata is not a publication waiver; only the resolved `benchmark_policy` from
recognized evidence can make Tier 2 or Tier 3 optional. An unrecognized `true`
claim can conservatively require a tier, but an unrecognized `false` claim
cannot waive one.

Agent-evaluation payload metadata and its summary are duplicated claims at the
same precedence level and must agree. A conflict between valid booleans at that
level resolves to required evidence. Invalid entries do not count as policy
values; when the level contains no valid boolean, resolution falls through to
the next lower-precedence source, and no valid value anywhere means required.
The consistent payload/summary claim takes precedence over recognized peer result
metadata. Conflicting booleans among peer results likewise resolve to required
evidence so aggregation order cannot create a publication waiver.
Every Tier 1, Tier 2, and Tier 3 result used for publication carries a
`publication_target` with the exact NFC filesystem-entry name, a SHA-256 source digest,
and the versioned `skill-evaluator-source-tree/2` recipe. The recipe binds
author-owned relative paths, node kinds, executable bits, and file contents
while excluding only known generated artifacts. In particular, authored
`evals/` inputs are included. The v2 exclusions are any-depth `.git`, `.venv`,
`__pycache__`, and `node_modules`; root `.evals`, `.results`, `.versions`,
`results`, and `versions`; `evals/results`; and the generated root files
`BENCHMARK.md`, `skill-card.md`, and `skill.oms.sig`. Filesystem case aliases
are treated according to the host filesystem, while a case-distinct authored
name on a case-sensitive filesystem remains covered. A same-named file below
another authored directory is still included. Tier 3 runtime projection and
full `--copy-repo` staging omit the same generated inputs so excluded generated
bytes inside the target cannot affect evaluation evidence. Tier 1 and Tier 2
skip the generated-artifact names (`results`, `versions`, `evals`, their dot
variants, `BENCHMARK.md`, `skill-card.md`, and `skill.oms.sig`) at any depth.
When one of those names appears below the target root, the digest would certify
content that no scan read, so the Tier 1 run records the path and publication
stays `INCOMPLETE` until it is renamed. The root `evals/` directory holds Tier 3
inputs and is outside the Tier 1 scans by design.
Split-job results must match this identity exactly. Tier 3 runs that stage any
linked/full repository context or external reference/workspace skills, or task
inputs and custom environments that carry `.git`, `.venv`, `__pycache__`, or
`node_modules` entries, remain runnable but are marked `INCOMPLETE`, because
that projection is not fully determined by this target-only publication
identity. Legacy anonymous results
remain readable, but their publication status is `INCOMPLETE`.

Built-in Tier 1 and Tier 2 results also carry a versioned
`publication_evidence` object with exact `schema_version`, `producer`, `tier`,
and canonical `check_id` fields. Reporters accept only the documented built-in
producer/check combinations. This marker is provenance inside trusted local or
CI artifacts; it is not a cryptographic signature for accepting result files
from an untrusted party.

Publication model, evaluator, environment, and skill identities reject reserved
placeholder text after Unicode confusable-skeleton comparison. This prevents a
visually spoofed placeholder such as one containing a Cyrillic or Greek letter
from becoming publication evidence while preserving ordinary multilingual
identities.

Payload and summary policy claims are accepted only when their containing
evidence matches that exact publication target; evidence from another source
cannot waive a required tier. A skipped Tier 3 payload must satisfy the same
target binding before its policy can waive evidence. A completed Tier 3 payload
also duplicates its run-owned `run_id` in the payload and summary; missing or
contradictory run identity is incomplete publication evidence.
When multiple complete Tier 3 payloads disagree, reporters select the most
conservative effective verdict (`FAIL`, then `NEUTRAL`, then `PASS`) before
applying deterministic tie-breakers.

Execution controls do not rewrite that publication policy. `--no-dedup` and
`--tiers 1,3` select which validators run, while `--no-block-on-dedup` changes
whether Tier 2 affects the command exit code. None of those flags persists a
publication waiver. Without explicit policy metadata, a run that omits Tier 2
therefore exits according to its CLI gate but still produces an `INCOMPLETE`
publication card.

### Evaluated source provenance

The Evaluation Metadata section distinguishes the source tree that was evaluated
from the evaluator build that evaluated it:

```text
- Evaluator version: `0.8.2`
- Evaluated source: `NVIDIA/NVFlare`
- Evaluated source revision: `2263a2ebdab903e87f7e7c0a001d22c3a926a9cf`
- Evaluator container revision: `ghcr.io/nvidia/skillevaluator@sha256:0117bc2e...`
```

Without that separation, two skills evaluated from different repositories by the
same evaluator container publish cards whose only recorded revision is the shared
container tag, and a reader cannot tell which version of a skill was evaluated or
whether the card has gone stale.

The identity is supplied by the orchestration input and carried through the
evaluation-result contract unchanged. It is never inferred from repository state
while rendering, because the tree that renders a card is the evaluator checkout
rather than the evaluated skill's source. The supported seams are:

- `--evaluated-source-repository`, `--evaluated-source-revision` and
  `--evaluator-container-revision`, accepted by both `validate` and
  `tier3 evaluate`, which record the identity on the card and, for a Tier 3 run,
  persist it into that run's `run_config.json`;
- the `evaluated_source` argument to `build_agent_eval_payload` or
  `agent_eval_result_from_directory`;
- an `evaluated_source` object in the run's `run_config.json`. Note that
  SkillEvaluator writes that file itself, so a publication pipeline using this
  route has to add the key to the generated run artifact before the card is
  rendered;
- `metadata["evaluated_source"]` on any validation result, which is how a card
  that publishes without a completed Tier 3 run records its identity.

Where any two carriers supply a field and disagree, rendering fails rather than
silently choosing one, so the order results happen to arrive in can never decide
which source tree a card names. `Evaluated source revision` records a full Git
object id of 40 or 64 hex characters, or a canonical `sha256`/`sha384`/`sha512`
digest of the evaluated skill content at that algorithm's own width when a run
has no upstream commit. A short revision prefix is refused, because it can grow
a second match as a tree grows. `Evaluator container revision` records an image
reference validated component by component: a repository path of at most 255
characters, an optional tag of at most 128 characters, and an optional digest at
its own algorithm's width. The 255 bound measures the path once the registry
host has been split off it. Path components are lower case, as the OCI grammar
requires, while a registry host may use any case and is read as a host only when
it is `localhost`, carries a dot, or carries a port. A bare name is refused
because it identifies a repository rather than the build that ran, and a
published PASS additionally requires the digest, or a full implementation
revision, because a tag can be repointed after the card is published. Fields
the orchestration did not supply render as
`not recorded (not supplied by the orchestration input)`.

Keep the file with the skill and refresh it whenever the skill, eval dataset,
agent/model, evaluator version, scoring policy, attempt policy, or execution
environment materially changes. Follow the
[rollout and backfill runbook](benchmark-rollout.mdx) when regenerating existing
published cards.

## Safety guarantees

Report writes are hardened: every file is written atomically (a temporary file
renamed into place), and SkillEvaluator refuses to write through symlinks,
Windows junctions, or paths with parent traversal. A run that is interrupted
mid-write never leaves a half-written report, and a report path can't be used
to redirect output somewhere unexpected.

## Tier 3 results on disk

`tier3 evaluate` does not use `-r`/`-o`. It writes a results tree to the first
of:

1. `--results-dir <dir>` on the command line
2. the `SKILLEVALUATOR_RESULTS_DIR` environment variable
3. `<skill>/evals/results/` (the default)

With an external root (the first two options), each skill gets its own
subdirectory — runs land under `<dir>/<skill-name>/`, not directly under
`<dir>`. Configured roots must be outside the skill. The canonical
`<skill>/evals/results/` path is the only supported in-skill result root; this
keeps generated runs outside the versioned source-tree digest used to combine
publication evidence.

Each run creates a collision-safe directory named by its run ID
(`YYYYMMDD_HHMMSS_<pid>_<12-hex-nonce>`). Where symlinks are supported, a
`latest` symlink points at the newest run; otherwise readers select the newest
completed run directly:

<FileTree>
- evals/
  - results/
    - latest/
    - 20260709_141530_12345_a1b2c3d4e5f6/
      - result.json
      - run_config.json
      - attempt_policy.json
      - report.html
      - comparison.json
      - codex/
        - lift.json
        - pass_at_k_lift.json
        - with-skill/
          - summary.json
          - trials/
        - without-skill/
          - summary.json
          - trials/
</FileTree>

- **`result.json`** — the bounded run summary: run ID, per-agent scores and
  lift, pass@k aggregates, the resolved run configuration, and execution
  status. When repeated case, security, or failure details would make this
  browser-facing file too large, `result_projection` records exactly which
  fields were omitted and points to the canonical per-agent JSON artifacts by
  relative path, byte size, and SHA-256 digest. The in-process return value
  remains complete; readers rebuilding a report from disk follow those
  artifact references.
- **`run_config.json`** / **`attempt_policy.json`** — exactly how the run was
  configured: environment, attempts, concurrency, grading mode, pass threshold.
- **`report.html`** — the human-readable report, generated automatically at
  the end of every run.
- **`comparison.json`** — the cross-agent comparison table; written only when
  you ran more than one agent.
- **`<agent>/lift.json`** and **`<agent>/pass_at_k_lift.json`** — per-metric
  deltas between the two arms; written only when both arms produced scores
  (a `--skip-baseline` or `--skip-with-skill` run has neither).
- **`<agent>/{with-skill,without-skill}/`** — each arm's `summary.json`
  (scores, dimensions, pass@k, trial counts) and a `trials/` directory of
  per-trial artifacts: the trial's `reward.json`, Harbor's `trajectory.json`
  when available, and redacted, size-capped diagnostic copies such as
  `trial.log`, `exception.txt`, and agent logs (`codex.txt`, `opencode.txt`).
  With standard grading, `reward.json` records `trajectory_source` (the
  trajectory or agent log that was graded) and, under each LLM judge's
  `details`, an `omitted` record showing whether its evidence was truncated to
  fit the [evidence budget](tier3-live-evaluation.mdx#evidence-budgets) or, for
  `behavior_check`, the final-response section limit
  (`SKILL_EVAL_BEHAVIOR_FINAL_RESPONSE_LIMIT`). For `behavior_check`, the
  record's `reason` names each setting that applied.

<Note>
  Read commands (`view`, `compare`, `create-eval-dataset --refine`) honor the
  same precedence, then fall back to the legacy `<skill>/evals/results/`
  location — so old runs stay visible after you configure
  `SKILLEVALUATOR_RESULTS_DIR`. Current timestamped runs are selected only when
  stable regular `run_config.json` and matching atomic `result.json` artifacts
  are present. Unmarked runs created before run-level `result.json` remain
  readable only when `run_config.json` has a recognized historical task source
  and complete agent metadata, and every configured agent has one stable,
  identity-matched summary satisfying the full historical score, dimension,
  pass-at-k, and completion schema. Authenticated summaries from before status
  fields are consumed as successful; coherent status-era failed summaries stay
  visible without contributing scores. Any marker presence prevents an
  incomplete current run from being interpreted as legacy output. The results
  tree is generated output: don't commit it.
</Note>

## Reading a live-eval report

### The terminal summary

A finished `tier3 evaluate` run prints two tables and closes with a compact
**Artifacts** panel. **Results by Evaluator** lists each evaluation signal
with its per-arm scores and Skill Lift; **Results by Dimension** rolls those
signals up into the five dimensions below. A metric the run couldn't score
renders as `NO SCORE` — it is never coerced to 0.0 — and unscored metrics are
omitted from the averages, so `overall_score` can be `null` in the JSON. In a
baseline-only run (`--skip-with-skill`) the with-skill and Skill Lift cells read
`skipped` instead, because that arm never ran. The
Artifacts panel shows the HTML report path, the output directory, and — only
when a retained Harbor jobs directory exists — a ready-to-paste `harbor-view`
command.

### Next steps for the run

Below the per-case fixes, the case summary in the terminal, `report.html`,
and the Markdown report list up to three **Next steps** for the run as a
whole: what a single case cannot show. The steps come from fixed rules, so
they also appear when no LLM is configured. Each step names:

- the **target** to change: the `evaluation` settings (re-run, more
  attempts), the `dataset` (more cases, negative controls), or the `agent`
  (compare agents or models);
- the **problem** observed in this run and the **evidence** behind it (case
  ids, attempt marks, or per-agent pass-rate changes);
- the **action** to take, with the flag or file to change;
- the **check** that would show the change worked.

| Step | Shown when |
|------|------------|
| Incomplete run | Attempts did not produce a score and no per-case run error already says so |
| Inconsistent results | A case passed on some attempts and failed on others (more `--n-attempts`) |
| Single attempt | Every case ran once |
| Agent-dependent effect | Two or more agents differ by 20 or more points in pass-rate change, and the best agent gains at least 10 points |
| More cases | Fewer than five skill cases ran, unless the case fixes already ask for new cases |
| Negative controls | The dataset snapshot has no case with `expected_skill: null` or `should_trigger: false` |
| Agent experiment | Only one agent ran and the skill showed no clear gain |

A step marked `hypothesis` is a cause or remedy to test, not a finding: for
example, that one agent follows the skill differently. A step marked
`limited` rests on an incomplete run, so re-run first. Steps never suggest
removing cases or loosening expectations to raise a score. Baseline-only runs
and runs where the skill never activated get no next steps. The Tier 3 payload
carries them as `next_steps`, with the `kind`, `target`, `problem`,
`evidence`, `action`, `check` and `strength` fields.

### The five dimensions

With `default` or `default_plus_custom` grading, reports lead with five
dimensions, each answering one question:

| Dimension | Question answered | Signals and source |
| --- | --- | --- |
| Security | Is it safe to use? | `security`, from deterministic trace checks |
| Correctness | Is the answer correct? | `accuracy`, from the `judge_accuracy` LLM judge |
| Discoverability | Was the right skill loaded when needed? | `skill_execution`, from deterministic trajectory checks |
| Effectiveness | Did the skill help complete the task? | `goal_accuracy` and `behavior_check`, from LLM judges |
| Efficiency | Did it avoid wasted tool or skill usage? | `skill_efficiency`, from deterministic trajectory checks |

Tool-efficiency checks classify explicit searches rooted at `/` as wasted work,
whether or not the command names the expected skill or script. Scoped searches
and `/` used as a search pattern retain their existing classification. This rule
recognizes common search commands, including ones with redirections or wrapped in
`sh -c`; it does not interpret expansions, comments, here-documents or other
dynamically constructed shell programs.


Every evaluator and dimension score is on a 0.0 to 1.0 scale. The generated
standard grader rejects non-finite values and clamps numeric scores with
`max(0.0, min(1.0, score))`. A failed required judge produces no score instead
of a numeric zero. The fixed dimension bands are **pass** at 0.50 or above,
**neutral** from 0.40 to below 0.50, and **fail** below 0.40.

`run_config.json` records the configured judge provider, model, source, and
catalog-verification status separately from the agent model. `result.json`
embeds that run configuration alongside the scores. This provenance makes the
LLM-judged values traceable, but it is not evidence that the judges are
validated. The repository does not publish inter-rater agreement, calibration
results, or a comparison against human-labeled ground truth.

The **Quality Score** displayed out of 100 in the HTML report is the Tier 1
static-analysis score. It is not an input to the Tier 3 dimensions, overall
score, or Skill Lift.

For standard grading, each arm's Overall is the mean of the dimensions it
scored, and each dimension is the mean of its scored metrics. N/A dimensions
and metrics are excluded rather than counted as 0 or 1.

This per-arm rule is shared by the report, per-attempt pass@k thresholding, Skill
Lift, comparisons, and best-agent selection. Standard artifacts identify it as
`skill-evaluator-dimension-mean-v1` in `score_policy` and in the persisted
attempt policy. Older metric sets and partial historical artifacts keep their
legacy policy rather than being rescored as current data.

Overall comparisons require both the same scoring policy and the same metric
set. A shared policy name alone does not make five-metric and six-metric means
comparable. When two conditions use different metric sets under the same
policy, their individual scores and shared per-metric deltas remain available,
but overall Skill Lift and the pass@k comparison are omitted. Reports containing
agents scored on different standard metric sets retain their individual scores
and mark the overall comparison as incomplete, without selecting a best agent.
A custom-only agent, one whose conditions use only its grader's own overall
(`custom-overall-v1`), is still ranked against standard agents by that score,
and `tier3 compare` shows it beside them. `tier3 compare` refuses standard
agents scored under different policies or metric sets.

### Skill Lift

Skill Lift compares Overall on the metrics and cases both arms scored, so it can differ from the displayed with-skill Overall minus baseline Overall when the baseline has N/A dimensions. It uses the same score units as both arms and ranges from
-1.0 to +1.0. Because live agent runs are noisy, especially at low attempt
counts, small deltas are kept neutral. The verdict bands:

| Lift | Verdict | Read it as |
| --- | --- | --- |
| ≥ +0.05 | Pass | Positive observed lift; publication still requires the dimension and evidence gates |
| between −0.10 and +0.05 | Neutral | Within the neutral band; raise `--n-attempts` for more evidence |
| ≤ −0.10 | Fail | The skill makes the agent worse — investigate before shipping |

These bands color-code Skill Lift as diagnostic evidence. They do not determine
the combined `validate --tier3` or `BENCHMARK.md` verdict. The overall verdict
comes from the five dimensions: **PASS** when at least one successful agent has
all five dimensions at 0.50 or above; **NEUTRAL** when no agent passes but at
least one has no dimension below 0.40; and **FAIL** when every successful agent
has a dimension below 0.40.

A +0.03 lift therefore remains neutral under these bands. Lift requires both
arms; if you ran with `--skip-baseline`, there is no lift to report. In
`custom_only` grading, your own grader defines the score and lift — see
[Custom Graders & Tasks](custom-graders.mdx).

When the HTML report has no lift for an agent or dimension, its label says
why. **no baseline** means that row has no baseline score, for example after
`--skip-baseline`. **comparison unavailable** means a baseline score was
recorded but cannot be compared with the with-skill score, for example because
the arms used different score policies or no case kept matching judge models.

For each LLM metric (`accuracy`, `goal_accuracy`, and `behavior_check`), cases
that used different judge models across the arms are excluded from that
metric's lift. This includes model changes across repeated attempts or the
scoring steps of a multi-step task. `lift.json` records the excluded case
counts by metric in `judge_mixed_cases`. Arm scores still describe all scored
cases, while evaluator, dimension, and overall lift use the eligible
comparisons. A reported lift can therefore differ from subtracting the two
displayed arm scores, even reversing their apparent direction. When no complete
comparison with matching judge models remains, the affected metric, dimension,
and overall lift are unavailable rather than zero.

If every positive with-skill trial has confirmed zero activation, the agent's
result is **INCONCLUSIVE: skill never activated**. Reports keep its arm scores
and diagnostic trials but suppress its evaluator, dimension, overall, custom,
and pass@k lift comparisons and skill-quality advice. Negative controls do not
count as activation opportunities; missing or unsupported evidence remains
unknown. Eligibility is determined separately for each agent, so another
agent with observed activation can still contribute a comparison.

### Measured agent resources

Each agent's canonical JSON payload contains a `resources` object. The HTML
table shows total prompt plus completion tokens, agent execution seconds, LLM
seconds, tool seconds, and LLM milliseconds per token for each arm, telemetry
coverage, and the with-skill-minus-baseline difference. A negative difference
means less use with the skill; the HTML percentage divides it by the baseline.
Routing/tool-productivity efficiency remains a separate score. Missing counters
and incomplete arms produce null totals or deltas (`N/A` in HTML). Resource
deltas require matching case counts and complete measurements in both arms;
they do not measure evaluator tokens, setup time, price, or statistical savings.

| Measurement | Meaning |
| --- | --- |
| Agent execution seconds (`agent_seconds`) | Harbor's measured agent phase from the trial's `result.json`. Environment setup, agent installation, and verifier time are excluded. |
| LLM seconds (`llm_seconds`) | Model time from the trial's ATIF trajectory. With native ATIF timing (source `atif`), the sum of `llm_duration_ms` when every agent step records it. Otherwise it is inferred from step timestamps (source `step_timestamps`): each gap between steps counts once, and the part not spent in a tool is LLM time, which then also includes harness and queue time. |
| Tool seconds (`tool_seconds`) | Tool execution time. Native timing takes the union of tool-call intervals, so overlapping calls count once. Inferred timing reads the `Wall time` that Codex writes in the header of its shell and `apply_patch` tool output, never from the command output, or the `duration_seconds` Harbor keeps for those calls; parallel calls on one step count their longest wall time. A trajectory without tool calls measures 0 seconds. |
| LLM ms per token (`llm_ms_per_token`) | `1000 × LLM seconds / (prompt + completion tokens)` over the arm's totals. It needs complete LLM-time and token totals and a positive token count. |

Each trial's `timing` object records `llm_seconds`, `tool_seconds`, and
`source`, and `resources.timing_sources` lists the sources each arm used. If
the measurements mix native and inferred timing, `resources.caveats` contains
`mixed_timing_sources` and the HTML report says the LLM and tool seconds are
not like-for-like.

Inference covers trajectories whose tool calls are all Codex shell tools
(`exec_command`, `write_stdin`, `wait`, `wait_command`, `shell`, and
`shell_command`) or `apply_patch`, each with a recorded wall time. A trial that
also calls a tool with no recorded duration, such as web search,
`update_plan`, or an MCP tool, or whose step timestamps are missing, lack a UTC
offset, or run backwards, has no LLM or tool time. Inferred timing also needs
the agent's next step right after each tool step: a user or system step there
can follow idle or user time, so the trial has no timing. Agents without native
timing or Codex `Wall time` headers are timed only when their trajectory has no
tool calls.

Each step of a multi-step task is timed on its own, so the time between Harbor
steps is not counted. Steps marked `is_copied_context` repeat context from an
earlier trajectory and are not timed; a copied step after new steps leaves the
trial without timing. Copied timestamps do not show when the first new response
started, so inferred timing also leaves the trial without timing when the new
steps after copied context start with an agent step.

Trials whose `trajectory.json` was omitted (too large, or redaction or
validation failed) and multi-step trials scored per step have no timing.
Missing timing stays `N/A` (`null` in JSON), never zero, and follows the same
complete-arm and matching-case rules as tokens. Timing is diagnostic and does
not change scores, verdicts, or gates.

### Failure reasons and per-trial rows

Each evaluator card lists its per-trial evidence by eval case with the
grader's reason, and a failing card (with-skill score below 0.60) opens the
list. A case that scored below 0.80 also quotes a short excerpt of the
offending command or artifact when the grader recorded one. When the attempts
of one case disagree, the lowest-scoring attempt's reason is shown. In the
**Per-Evaluator Drill-Down** table, hover a dotted-underlined score below 0.80
to read the reason for that trial.

Reasons are built from each trial's `reward.json` `details`, joining up to
three distinct parts from the grader's `reason` or `message`, failing findings
and behavior results, failed rubric criteria (except criteria the grader
excluded from the score), failed named checks, and the security attribution
note. The report redacts the values of configured credential environment
variables and recognizable credential patterns in reasons and excerpts, keeping
line breaks so a masked `key: value` pair ends at its line. It caps drill-down
reasons at 240 characters and excerpts at 300.
Secret detectors record their pattern rather than the matched text, so their
findings show a reason but no excerpt.

Reasons and excerpts are the first details dropped when a report is large. The
HTML page adds them only while its data stays within the page's preview limit
and says how many it left out, so they never displace the overview, dimension
scores or evaluator cards. The JSON download keeps them unless the embedded
payload reaches its 2 MiB limit; it then drops them before any other detail
and records the count as `failure_reasons` under `report_truncation.omitted`.

The drill-down has one row per trial for each agent and condition, with a
**Condition** column (`With skill` or `Without skill`); baseline rows are
listed even when they have no matching with-skill case, and a metric only
baseline rows scored still gets a column. When the HTML preview is bounded, it
keeps 64 with-skill rows across all agents and 64 baseline rows per agent, and a
note under the filter says how many rows it left out. The **Steps per Eval
Case by Agent and Condition** chart plots one series per agent and condition
from every trial, not only the rows the preview keeps, for up to 200 eval
cases; a note says how many more cases the JSON download holds. A case with
missing or partial step telemetry is a gap, not a zero.

### Per-case expectation diagnostics

The HTML **Dataset** tab expands each case into its authored requirements and
recorded judgments, separately for each agent, attempt and condition. The JSON
payload's `case_diagnostics` carries the same inventory. Requirements retain
their original text (with credentials redacted); behavior IDs use the source
field and zero-based position, while judge `step` numbers remain one-based.
Routing and script checks use their named sub-checks, not the aggregate score.
Expected output is checked separately for goal achievement and accuracy; an
excluded accuracy criterion is listed as inapplicable, never as unmet.

Each judgment has one of five statuses:

| Status | Meaning | Next diagnostic step |
| --- | --- | --- |
| Met | An explicit verdict supports the requirement | No correction indicated by this check |
| Unmet | An explicit verdict reports a violation | Compare the requirement with the observed evidence; inspect execution if it is valid, or correct the test if it is inappropriate |
| Not checked | No unique usable verdict: missing/truncated output, judge or execution error, ambiguous identity, or explicit judge abstention | Inspect the retained execution/judge artifacts and rerun before diagnosing a skill defect |
| Unscored | The grader did not score this requirement's metric | Inspect grader configuration and score output |
| Not applicable | The grader explicitly excluded this check for this condition | Confirm that exclusion is intended; do not count it as a failure |

Reasons and short evidence excerpts accompany the verdicts when recorded.
Excerpts are metric-level context, not proof automatically attributed to every
requirement. A low score alone never assigns ownership to the skill or test.
Negative controls may correctly avoid the skill while completing an unrelated
task; being unrelated is not a reason to remove the case. The no-skill baseline
can mark skill checks inapplicable while still judging the task outcome.
Intentionally skipped conditions do not create diagnostic attempts. Failed or
unknown conditions remain visible even when no trial result was retained.

Behavior judges may return `passed: null` with an explanation when evidence
does not permit a check. The rich behavior result's `expectations` retains all
original behaviors, including those missing from a salvaged response. Existing
conservative scoring is preserved: only explicit passes earn credit, and the
denominator remains the full expected behavior count. Unchecked entries can
therefore lower the score without establishing a verified defect.

Inventories are bounded to 512 cases, 128 requirements per case, 512 attempts
across the report and 8,192 judgments. Any omissions are recorded under
`report_truncation.omitted`. Oversized HTML previews omit whole diagnostic
inventories rather than truncating identity or status fields; JSON Downloads
retain them unless the canonical 2 MiB limit also requires dropping them.
Dropping an oversized diagnostic inventory preserves built failure reasons
whenever those reasons still fit within the canonical limit.
Retained run artifacts remain the source for details omitted by either limit.

### pass@k

pass@k is the reliability signal, reported separately from the dimension
scores. With `--n-attempts k`, each eval case runs k times per arm, and a case
counts as passed when at least one attempt clears the `--pass-threshold`
score using the same overall formula above. Comparing pass@k across arms (in
`pass_at_k_lift.json`) tells you
whether the skill makes success more *repeatable*, not just whether the average
score moved. Each arm also records a case-level 95% Wilson score interval for
its pass rate. When both arms contain the same identified cases,
`pass_at_k_lift.json` records the paired outcome counts — skill-only passes,
baseline-only passes, both-pass, and neither-pass — plus a two-sided exact
McNemar diagnostic over the discordant pairs. Partial or unidentified pairing
is labeled and does not receive that exact-test result.

Each logical attempt counts once: a multi-step native task's step rewards
combine into one attempt score for averages and pass@k. When one condition
mixes standard-metric and custom-only rewards, its overall score and lift use
that logical-attempt overall rather than the mean of the standard dimensions,
which would cover only the standard rows.

Case identifiers used as JSON keys must be printable, free of credential
material, and no larger than 512 UTF-8 bytes. A reward with an unsafe identity
is retained as a failed diagnostic but is not scored. For large evaluations,
`summary.json` keeps exact pass, attempt, failure, and pairing totals while
publishing bounded case, attempt, and failure-detail samples. The matching
`*_total`, `*_shown`, and `*_truncated` fields make every omission explicit;
sampling does not change the aggregate score or paired comparison.

The paired record also reports its pass-rate delta and the minimum p-value the
exact test could attain with the observed number of discordant pairs. When that
minimum is above 0.05, the report labels the test resolution-limited at that
threshold. This is a mathematical resolution limit, not evidence of no effect;
with five or fewer discordant pairs, a two-sided exact result cannot fall below
0.05 regardless of direction. The JSON always preserves compact decimal text
for both probabilities. It also records a reduced rational in each `*_exact`
field when the numerator and denominator fit both SkillEvaluator's 4,300-digit
safety cap and Python's active integer-string conversion limit. Otherwise that
field is `null`, `*_omitted` is `true`, and `*_omitted_reason` is
`"decimal_digit_limit"`. The numeric approximation is `null`, rather than a
false zero, if binary floating-point conversion underflows.

These uncertainty fields describe the cases in one configured run. They do not
make heterogeneous cases independent, correct dataset leakage, or promote a
small p-value into proof that a skill generalizes. Keep the dataset, attempt
policy, agent, model, and environment fixed when interpreting them.

## Browse results

### view

Opens the newest `report.html` for a skill in your browser, regenerating it
from the stored run data if the file is missing.

```bash title="Open the latest HTML report"
skillevaluator view ./my-skill
```

### compare

Prints a side-by-side terminal table of the most recent stored results per
agent — score and lift per evaluator — across everything under the results
root. Summaries whose execution status is anything other than `succeeded`
are ignored, so a failed run can't masquerade as a score.

```bash title="Compare stored results across agents"
skillevaluator compare ./my-skill
```

Both commands accept `--results-dir` to read from a non-default location.

### tier3 feedback

Opens a terminal chat about one completed run. Answers are grounded in that
run's scores, comparisons, per-case attempts, measured agent resources, and
saved feedback, without running the evaluation or regenerating its LLM feedback.
Pass the run directory itself; see
[tier3 feedback](cli-reference.mdx#tier3-feedback) for the options and what the
chat sends to the LLM provider.

```bash title="Discuss one run"
skillevaluator tier3 feedback ./my-skill/evals/results/20260709_141530_12345_a1b2c3d4e5f6
```

### harbor-view

Opens retained Harbor job artifacts in Harbor's own trajectory browser — the
deepest debugging view, down to individual agent transcripts. Staged-task and
raw Harbor job directories are transient: they are deleted after collection by
default, on success and failure alike. Pass `--harbor-keep-jobs` to retain
them — the retention outcome is recorded in the results, and the Artifacts
panel prints this command only when a retained jobs directory actually exists.
Retained jobs live under `_harbor-jobs/` inside the run directory.

```bash title="Browse retained trajectories"
skillevaluator tier3 evaluate ./my-skill --agents codex --env-mode docker --harbor-keep-jobs
skillevaluator harbor-view ./my-skill/evals/results/20260709_141530_12345_a1b2c3d4e5f6/_harbor-jobs
```

(`skillevaluator tier3 harbor-view` is the same command under its expert
alias.)

## Machine-readable contract

For CI and tooling, two JSON entry points matter:

- **Standalone `tier3 evaluate` runs** — parse `result.json` in the run
  directory (or follow `latest`). It carries per-agent scores, dimensions,
  lift, pass@k, trial counts, the attempt policy, and execution status.
  Unscored metrics stay unscored rather than defaulting to 0.0, so
  `overall_score` can be `null`.
- **`validate --tier3` runs** — the combined
  `skillevaluator-output-<timestamp>.json` report embeds the Tier 3 payload
  alongside the Tier 1 and Tier 2 results, so one file covers all three
  tiers. Each built-in Tier 1 or Tier 2 result carries its validated
  `publication_evidence` producer marker alongside finalized gating metadata,
  and the top-level
  `benchmark_policy` records whether Tier 2 and Tier 3 evidence is required for
  publication. `publication_status` is the compact machine-readable verdict;
  `publication` carries eligibility, reasons, and the Tier 3 evidence status.
  This is intentionally separate from `overall_status`, which continues to
  describe the command/process gate. Tier 3 is advisory for the CLI exit code by default and becomes
  blocking with `--block-on-agent-eval`; Tier 2 is blocking for the exit code
  by default and becomes advisory with `--no-block-on-dedup`. Those exit-code
  controls are separate from `benchmark_policy`. A validator's independent
  policy failures, such as a quality score below its required minimum, appear
  in `gate_failures` when present. Check those alongside `findings`; changing
  finding severity does not waive the minimum-score gate. The terminal, HTML
  report, and `BENCHMARK.md` also show these failures.
- **The evaluated source identity**: every JSON report always carries a
  top-level `evaluated_source` object, resolved from every carrier the run
  recorded, so the JSON and `BENCHMARK.md` name the same source tree. It is
  `null` when the orchestration input supplied none. Carriers that name
  different sources abort the run before any report file is written, so a
  contradictory identity is never published in one format and reported in
  another.

Both paths speak the same dialect: standalone `tier3 evaluate` and
`validate --tier3` share one HTML renderer for `report.html`, and both embed
the Tier 3 payload at schema version `2.0`. In that payload, conclusions and
recommendations written by the LLM carry `source: "llm"` and name the model
that wrote them as `model`. For a Claude 5.5 or later model on the native
Claude API this is the model the reply names, which can be the server-side
refusal fallback model rather than the configured model. Otherwise it is the
configured model, unless a server-side `fallback` block in the reply names
another model.

Exit codes and a ready-made JSON gating recipe live in
[Gate Your CI](ci-integration.mdx).
